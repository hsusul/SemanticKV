# SemanticKV Evaluation Report

SemanticKV evaluates semantic-aware prefix-cache eviction for LLM serving workloads using a deterministic simulator. The goal is not to claim real GPU speedups, but to test whether semantic block identity and online feedback can improve cache behavior under controlled memory pressure.

## Motivation

LLM serving systems benefit from prefix/KV caching when requests share prompt prefixes. Under tight memory budgets, cache eviction controls whether the system keeps high-value reusable blocks such as system prompts, templates, retrieved context, tool outputs, or legal evidence. Generic cache policies do not explicitly model these semantic differences.

## Methods

Each experiment generates deterministic `PromptRequest` streams from a fixed random seed. The simulator segments prompts into semantic blocks, hashes normalized content, admits or accesses cache blocks, applies an eviction policy, and records simulated metrics.

Estimated TTFT is computed as:

```text
estimated_ttft_ms = base_ttft_ms + uncached_prompt_tokens * token_latency_ms
```

This is a structured approximation for policy comparison, not measured GPU latency.

## Workloads

- `low_memory_rag_stress`: large shared retrieved-context blocks, unique user queries, tight cache budget.
- `shared_system_prompt_high_reuse`: stable system and template blocks reused by nearly all requests.
- `tool_agent_session_reuse`: tool schemas are global, tool outputs are reused within short sessions, ephemeral outputs churn.
- `legal_review_long_context`: repeated legal instructions, evidence templates, and long evidence blocks.
- `workload_shift_static_vs_adaptive`: first phase emphasizes system/template reuse, second phase emphasizes retrieved-context reuse.

## Baselines

- FIFO
- LRU
- LFU
- Size-aware LRU
- Static semantic weighting
- Adaptive semantic weighting

## Metrics

- Avg simulated estimated TTFT
- p50/p95 simulated estimated TTFT
- Cache hit rate
- Relative improvement vs LRU
- Prefill tokens saved
- Hit rate by semantic type
- Eviction count by semantic type
- Adaptive semantic weights over time
- Cache memory utilization over time
- Eviction regret events

## Interpretation

Semantic-aware policies perform best when reusable prompt regions have stable identities and compete with large one-off user blocks under memory pressure. In the low-memory RAG and workload-shift experiments, adaptive semantic eviction substantially improves simulated TTFT versus LRU by avoiding user-query churn and preserving reusable retrieved-context or template blocks.

LRU remains strong on legal-review and tool-session workloads because recency is a good proxy for reuse in those scenarios. This is a useful evaluation outcome: SemanticKV is not tuned to make adaptive win everywhere, and the reports show where semantic admission helps versus where temporal locality remains sufficient.

### Why Adaptive Wins Under Low-Memory RAG Stress

The low-memory RAG workload creates a small set of large retrieved-context blocks that are reused by many requests, while user queries contain high-cardinality one-off text. LRU admits the unique user blocks and can displace reusable retrieved context because the recent user block looks valuable in the short term. Adaptive semantic eviction assigns higher value to retrieved context after hit/regret feedback and is more willing to reject low-value user churn under pressure. That preserves shared context and reduces simulated prefill work.

### Why Adaptive Wins Under Workload Shift

The workload-shift experiment starts with system/template reuse and then shifts toward retrieved-context reuse. A purely temporal policy has to relearn through eviction side effects, while static semantic weighting cannot change priorities after the shift. The adaptive policy records semantic weight history and updates weights from feedback, so retrieved-context blocks become more valuable once the traffic pattern changes. In the current deterministic run, adaptive and static semantic policies tie on simulated TTFT, but adaptive reaches the result with far fewer evictions, which indicates a cleaner cache state under the same pressure.

### Why LRU Wins On Some Session-Local Workloads

LRU wins on legal-review and tool-agent session workloads because the reuse pattern is local and recent. In those traces, the next useful block is often the block that was just used in the same session. Semantic type is less informative than temporal locality, and adaptive admission can be too conservative for ephemeral but immediately reused blocks. This is a credible negative result: it shows the project is evaluating policy fit, not tuning every workload to favor the proposed policy.

### Implications For Real LLM Serving Systems

The main systems implication is that semantic-aware eviction should be evaluated as a workload-dependent policy, not a universal replacement for LRU. It is most promising for multi-tenant RAG, shared enterprise system prompts, stable templates, and traffic shifts where high-value prompt regions are reused across users or sessions. For session-local agents with short reuse windows, LRU or hybrid recency-heavy policies may remain better.

Honest negative results improve credibility because production serving policies are rarely globally dominant. A hiring manager or infrastructure reviewer should see that SemanticKV can identify where semantic admission helps, where it does not, and what measurements would be needed before real deployment.

## Limitations

- TTFT is simulated and estimated, not measured from a GPU server.
- The cache stores metadata, not real KV tensors.
- Workloads are synthetic and deterministic.
- The semantic classifier is rule-based.
- No claims are made about production latency without backend calibration.

## Future Real-Serving Integration

Future work can integrate with vLLM, SGLang, or Ray Serve when cache telemetry and eviction hooks are available. A credible validation plan is:

1. Collect real prompt-prefix traces, cache hit/miss telemetry, block sizes, and measured prefill latency.
2. Calibrate `token_latency_ms`, memory-cost estimates, and block-size assumptions against backend measurements.
3. Replay traces through SemanticKV using the same cache capacity envelope.
4. Compare predicted policy deltas with measured backend outcomes.
5. Only then introduce backend-specific admission/eviction hooks.

## Real-Serving Validation Path

The current simulator limitation is that synthetic experiments use a configured TTFT formula. This is useful for controlled policy comparison, but it is not production evidence. Trace replay narrows that gap without requiring GPUs or backend internals.

The trace telemetry needed for offline validation is:

- request timestamp, session ID, tenant ID, and model name
- semantic prompt blocks with token counts
- anonymized block hashes instead of raw text when traces contain sensitive data
- observed TTFT if available
- observed prefix-hit tokens and prefill tokens if the serving backend exposes them
- optional total latency and cache metadata

SemanticKV now supports JSONL, JSON, and CSV trace loading. The anonymization helper can hash block text while preserving semantic type and token count, which is the minimum useful signal for cache replay without storing private prompts.

Latency calibration fits a simple linear model from observed TTFT and observed prefill-token counts:

```text
calibrated_estimated_ttft_ms = fitted_base_ms + uncached_tokens * fitted_ms_per_uncached_token
```

Offline trace replay then asks a counterfactual question: on the same request sequence and cache budget, how would each policy behave under the simulator's calibrated latency model? The result is still simulated, but it is grounded in serving-style telemetry rather than only synthetic workload generation.

This avoids benchmark theater because the project does not claim adaptive eviction was deployed or accelerated a GPU server. It separates:

1. simulator policy behavior,
2. latency-model calibration,
3. offline trace replay, and
4. future backend integration.

A future vLLM, SGLang, or Ray Serve integration should start as observability only, validate simulator predictions against real traces, and add cache-control adapters only where the backend exposes safe admission or eviction hooks.
